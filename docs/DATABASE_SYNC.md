# Database snapshots and Git sync

`looking-glass database` works directly on a project's
`.looking-glass/state.sqlite3`, without HTTP or an API token. Set `--root PATH`
before the operation. Without it, the CLI finds the nearest ancestor containing
a token or database, including a restored project that has never been served.
For a fresh clone with no local metadata yet, use `--root .`.

## Commands

```bash
looking-glass database --root ~/project dump -o looking-glass.sql
looking-glass database --root ~/project dump > looking-glass.sql
looking-glass database --root ~/clone restore looking-glass.sql
looking-glass database --root ~/clone restore --force looking-glass.sql
looking-glass database --root ~/clone restore - < looking-glass.sql
looking-glass database --root ~/clone check
```

`dump` writes SQL only, with no progress text on stdout. `--output` / `-o` defaults
to `-` (stdout). File output uses a temporary file in the output directory and
atomic replacement, so an invalid database or failed export leaves the earlier
snapshot intact. The parent directory must exist. The CLI refuses to save a dump
inside `.looking-glass/`, keeping it separate from private runtime files.

Export is safe while the server is running: SQLite's backup API takes a consistent
snapshot, including committed write-ahead-log (WAL) changes and excluding
uncommitted writes. Export validates the snapshot before writing any SQL.

`restore` validates the dump in a disposable database before opening the target.
It accepts the versioned SQL format produced by `dump`; other formats are rejected.
The SQL authorizer allows ordinary tables/indexes, inserts, transaction controls,
the format's pragmas, and its text-escape function. Attached databases, virtual
tables, triggers, and arbitrary functions or extensions are rejected.

Restore refuses an existing target unless `--force` is supplied. With `--force`,
the current state, including committed WAL changes, is backed up to a uniquely
named `.looking-glass/state-backup-*.sqlite3` before replacement. The JSON result
contains `ok`, integrity and foreign-key results, table counts, and `backup`
(an absolute path, or `null` for a fresh target). Installation uses a SQLite
backup transaction, preserving WAL bookkeeping rather than deleting sidecars or
swapping a file beneath open SQLite connections. Invalid input leaves the target
unchanged and creates no backup.

Stop **all** servers for the project before restoring, including servers embedded
outside the CLI. CLI servers hold shared cross-process SQLite maintenance leases;
restore requires an exclusive lease and is rejected while any CLI server is running. Browser
directory switches retain leases for visited projects until that server exits;
this also protects requests finishing against the previous workspace. The lease
is automatically released on process exit. The local maintenance database is
ignored with the rest of `.looking-glass/`.

`check` opens the existing database read-only, without initializing or migrating
the project. It verifies the core Looking Glass schema, SQLite `integrity_check`,
and all declared relationships with `foreign_key_check`, and reports row counts
for every user table. Missing or size-mismatched attachment files appear as
warnings, because those bytes are stored separately. A healthy database returns
`ok: true`; integrity/schema/SQL/filesystem failures go to stderr and exit nonzero.
Missing databases are errors, never silently created. Legacy core schemas are
accepted; opening the restored project in the app applies existing migrations.

## What moves between machines

The snapshot contains every ordinary database table and explicit index:
discussions and messages (IDs, authors, timestamps, resolved state, anchors),
source-marker metadata, snapshots, immutable review origins, compressed original
context, review drafts/edits/heads/anchors, managed images and annotations, PDF
bookmarks, and attachment metadata.

Tokens, the user-level project registry and server addresses, attachment upload
bytes, recoverable trash, browser tabs/selection/undo/layout, ordinary project
files, and Git history are outside the database. Restore never writes project
documents or approves review drafts. It neither copies credentials nor registers
an address. Starting the app generates a new token if needed; existing tokens
and upload files are preserved. Copy `.looking-glass/attachments/` separately by
your chosen file-transfer method if those uploads are needed on the other machine.
Managed images' original/current bytes are already in the database; local cached
image copies can be regenerated by the app.

Workspace-relative file keys work at a different checkout location. References
to files opened outside the workspace remain absolute and require the same files
at those paths. Historical Git-root metadata stays as captured; it is not
rewritten to the new machine. Keep project documents, embedded source markers,
and Git history in sync alongside the SQL snapshot so current anchors and
review baselines match the content being restored.

## Git workflow and conflicts

Keep `.looking-glass/` in `.gitignore`. Choose one named snapshot outside that
directory and commit it explicitly alongside the project files it describes.
No command stages, commits, pulls, or pushes automatically.

Before moving to another machine, export, inspect the diff, and commit/push.
On the receiving machine, stop the server, export any local changes you want to
keep, pull, restore (with `--force` if state already exists), check, and restart.
This is whole-state transfer, not bidirectional database merging. Two machines
can allocate identical IDs for unrelated messages, threads, or reviews. Resolve
SQL conflicts by selecting a complete snapshot and retaining the other snapshot
separately for reference; a clean Git merge alone does not prove the combined
state is meaningful. Do not restore conflict markers or hand-merged histories.

Dumps have a fixed `-- Looking Glass database dump v1` header, no export timestamp
or machine-specific header, sorted tables/indexes, and rows sorted by primary
key with binary ordering and remaining columns as tie breakers. Each row is one
`INSERT` line with explicit columns. SQL quotes are escaped, Unicode remains
readable, and CR/LF/NUL characters use bounded `replace(..., char(...))` expressions to keep rows on one
physical line. BLOBs use hexadecimal literals; compressed review context and
managed image bytes remain lossless binary content represented as text, with
less readable diffs than discussion text. `PRAGMA user_version` is preserved.
Unchanged logical state produces identical dumps, independent of WAL/checkpoint,
insertion order, and vacuuming. Changing a large row replaces its whole SQL line.

Snapshots include discussion text, original document contents, review proposals,
and image data. Review the snapshot and repository access before sharing.

## Recovering a local backup

Backups stay local and are full SQLite databases. To turn a returned backup into
a validated SQL snapshot without changing the active state, copy it into a
disposable project's `.looking-glass/state.sqlite3`, then export it:

```bash
mkdir -p /tmp/looking-glass-recovery/.looking-glass
cp /path/to/project/.looking-glass/state-backup-EXAMPLE.sqlite3 \
  /tmp/looking-glass-recovery/.looking-glass/state.sqlite3
looking-glass database --root /tmp/looking-glass-recovery dump -o recovered.sql
looking-glass database --root /path/to/project restore --force recovered.sql
```

Stop the project's server before the final command. Keep the backup until the
restored project has been checked. A failed backup prevents replacement.
